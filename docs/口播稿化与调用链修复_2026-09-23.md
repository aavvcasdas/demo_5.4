# 口播稿化与调用链修复（2026-09-23 第 2 轮）

本轮由用户四条纠正触发，原话：

1. 「请在 github 上搜索 star 多的口播稿生成项目，主要是要偏向口播的，国内的，多搜几个。**现在是偏向小说的，请修改小说那种长的设定修改成口播稿的**。」
2. 「**不是说需要这么多代码去生成的是很好修改，而是生成文章的时候就应当生成好了。**」
3. 「**是不是调用生成人生副本剧本的 skill 一直有误！这个重点去检查下。** 本身应该是不需要这么多代码来去删除修改文章的呀！而且这么修改的文章百分百有问题。」
4. 「**这是口播不需要修改 ai 味但是不要流水账就行**，例如这个文件 `fuben_craft_scan.py`。**我让你的审核是生成完再次查看并搜索网页的意思。**」

上一轮的记录见 [skill诊断与优化_2026-09-23.md](skill诊断与优化_2026-09-23.md)（第 1 轮：手艺层与语料接线）。

**口播稿没有章，只有秒。**

### 1.3 实测：交付稿的篇幅与排版都不在账号带上

对 `拆文库` 18 篇语料原文、红绿样夹具、79/80 交付稿做同口径测量：

| 样本 | 字数 | 行数 | 均行长 | 最长行 | >22字行 | 空行段 | 全篇标点 |
|---|---|---|---|---|---|---|---|
| **语料原文**（真抖音 ASR，18 篇） | 2,262–4,540 | 229–435 | **8.5–10.7** | 24–39 | 0–1% | **0–1** | **0–5** |
| **回归夹具**（作者自存绿样／红样） | 712 / 1,119 | 40 / 65 | **17.2–17.8** | 41 / 55 | 25–26% | **0** | **0** |
| **交付稿** `作品/79` / `作品/80` | 1,565 / 1,117 | 218 / 151 | **7.2–7.4** | 16 / 17 | 0% | **62–63** | **0** |

三条硬结论：

1. **篇幅**：80 号 1,117 字 = 全长档下限的 **40%**，79 号 1,565 字 = **58%**。
   按 §2.9 一个场面要 ≥12 行逐拍，三个场面加蓄势与兑现就是 2,500 字起——
   **「没有剧情」首先是篇幅问题，不是笔法问题。** 装不下三个场面，就只能列节点，列出来就是流水账。
2. **排版三式并存，无人判定**：语料一行 ≈9.6 字（ASR 自然断句）、夹具一行 ≈17.5 字（一行 2–3 个意群用空格隔开）、
   交付稿一行 ≈7.3 字。仓里没有任何一条规则说哪种对。
3. **交付稿是电报体 + 散文诗**：均行长 7.2 字命中 v10.5 的病根定性「**电报体压缩、短行只许切分不许省成分**」；
   62–63 个空行段，而语料与夹具都是 **0 空行**——空行在提词器里不产生停顿，只把意群打散。

### 1.4 机检的 13 个 code，没有一个查创作

`scripts/fuben_engine.py` 的全部 finding code：

```
ACCOUNT_BRAND_CANDIDATE  AI_CHECKER  AI_STYLE_*  BAD_DATE_LOCK  BINARY_INPUT
CARD_UNIT_DRIFT  DATE_COUNT_MISMATCH  EMPTY_BODY  EQUATION_AMBIGUOUS
EXPLICIT_ARITHMETIC  MISSING_SETTING  NO_FACT_LOCK  NO_STATE_LEDGER
NUM_PATTERN  QUOTED_CHARACTER_COUNT  REPLACEMENT_CHARACTER  SCOPED_CHARACTER_COUNT
SETTING_CLAIM_CANDIDATE  UNQUOTED_COUNT_CANDIDATE  WEAK_STATE_LEDGER
```

全是**日期、算术、事实锁、账号品牌、输入完整性**。
**没有一个查钩子、笑点、共情、侧面描写、剧情。** 这不是 bug——`fuben_policy.json` 的 `scope` 写得很清楚：
「机械阻断只用于明确的输入/算术/契约错误……不自动判文笔、事实真假或流量」。
**问题是创作那一侧一直是空的**：机检不管，而本该管的手艺层没被加载（1.1）、口播规格被删光（1.2）。
于是「PASS 双零」被当成了写好了。
