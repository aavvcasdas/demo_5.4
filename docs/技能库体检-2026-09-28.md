## 1. 为什么现在都在「删多余的 skill」

### 1.1 渐进披露不是免费：listing 预算会**静默丢掉**描述

Skill 的第一层（metadata：name + description）是每次会话都常驻的。Claude Code 给这份 listing 的默认预算是**上下文窗口的 1%**（`skillListingBudgetFraction = 0.01`），单条描述另有 **1536 字符**上限（`skillListingMaxDescChars`）。超预算时的行为不是平均压缩，而是**从「最少被调用」的 skill 开始，整条丢掉描述**；被丢描述后 skill 只剩名字，匹配用的关键词没了，于是「装了但再也不触发」。

- 参考：<https://claudefa.st/blog/guide/mechanics/skill-listing-budget>（1% 预算 / 1536 字符上限 / 丢描述策略）
- 参考：<https://blog.serghei.pl/posts/agent-skills-101/>（"装更多 skill 不只是多花 token，过了阈值会静默删掉让你的 skill 可被发现的那段描述"）

**推论（本库直接相关）**：不是「装得多更吃亏」这么模糊——是**你为 A skill 写的那段长描述，可能把 B skill 的描述挤掉**。所以写长描述不是"更清楚"，是在替全库做减法。

### 1.2 数量拐点：2–3 个精炼 skill 最优，4 个以上反而变差

一篇 Agent Skill 的对照实验给出的增益：1 个 skill `+17.8%`、**2–3 个 `+18.6%（最优）`**、4 个以上骤降到 `+5.9%`；作者归因于**上下文负担（context burden）**——候选一多，"选工具"吃掉推理预算。同一篇还指出：**AI 自己生成、没有实战沉淀的 skill 约等于负优化**。

- 参考：<https://juejin.cn/post/7664762522156859446>
- 参考：<https://www.gm7.org/archives/155403>（Skill 过多 → 上下文负担、路由复杂度、治理成本上升）

### 1.3 比"多"更危险的是"像"

语义相近的 skill 会互相干扰。当 `pdf-reader / pdf-summary / pdf-analyze / document-parser` 的 description 都写"处理 PDF"时，模型开始在候选里纠结，甚至绕开 skill 裸跑。另一个独立机制是 **Context Rot**：上下文越长，模型对长输入的利用越不均匀，规则和描述越堆越容易被稀释。

- 参考：<https://zhuanlan.zhihu.com/p/2040978244174927582>（Listing 截断 / Context Rot / 相似 Skill 冲突 三层退化）
- 参考：<https://juejin.cn/post/7647438301877305370>（高频常驻、长尾进"可检索冷存储"）

### 1.4 业界共识的治理动作

| 动作 | 判据 |
|---|---|
| 常驻 vs 冷存 | 频次 × 风险 × 上下文污染；低频能力退出常驻、保留可找回 |
| 描述瘦身 | 描述 ≤ 150 字符，**触发词前置**（截断时活下来的是前 50 字符） |
| 单一职责 | SKILL.md 主体 ≤ 500 行 / ~5000 token，细节下沉 references |
| 定期清理 | 90 天零调用归档、重复合并、第三方重审；项目专属 skill 放项目内 |

- 参考：<https://atlan.com/know/ai-agent/ai-agent-skills/agent-skill-best-practices/>（≤500 行 / ≤1024 字描述）
- 参考：<https://www.webfuse.com/agent-skills-cheat-sheet>（三层加载与体积建议）

### 1.5 一句话

Skill 的价值不在数量，而在**能否在正确的时间、用最小的常驻开销看见正确的那一个**。删繁就简的本质是保护「触发精度」，不是省那点 token。
