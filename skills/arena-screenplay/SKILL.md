# Arena screenplay：剧本项目主入口

本 Skill 管的是**可表演、可拍摄的剧本**，不是「人生副本」口播文案、文章、小说章节，也不是分镜/生图提示词。项目的第一原则是：**每场有人的目标、阻力和可见行动；行动造成状态变化；对白在争取或回避，而不是替作者解释。**

## 先分流，禁止静默混写

- 用户要主播从头念的第二人称稿：仍走 legacy `fuben-write`，不要套本项目的场景格式。
- 用户要人物在画面里行动、说话、被阻拦的剧本：走本 Skill，主产物是 `剧集/EP001/剧本.md`。
- 用户给了口播稿，要求「改成剧本」：先把旁白拆成场景、人物行动和冲突；不能只把每行前面加 `场 1`，也不能把旁白保留成一篇文章再叫它剧本。
- 用户只说「审一下」：先确认对象是剧本还是口播稿；本项目的机械检查永远不等于审美通过。

## Arena 项目契约

一个项目只有一份当前剧本。约定目录：

```text
项目简报.md                         # 本集观看承诺、人物目标、限制
剧集/EP001/剧本.md                   # 唯一当前正文
审核/EP001.md                        # 与剧本哈希绑定的审读记录
剧集/EP001/screenplay-index.jsonl    # 可选：由外部工具生成的派生索引
```

不要把 `正文.md`、`03_初稿.md`、`04_审读与返工.md`、`审核报告.md` 多份都当成当前正文。草稿可以留在 `运行/`，但交付和审读必须明确 `body_path`；正文变了，旧审读自动失效。

## 执行流程

### 1. 锁定本集最小契约

在写场景前，用几句话锁定：

1. 观众第一分钟应该获得的观看体验；
2. 主角此刻要什么；
3. 具体阻力是谁/什么，为什么不会立刻让路；
4. 主角为推进目标做的不可替代动作；
5. 本集兑现、代价和退出状态；
6. 时长、拍摄条件、人物数量和内容红线。

只有一个点子时可以在上下文中排因果，不强制落一套「场次单＋爽点表」。一旦真实分叉影响人物、关系或结局，再向用户确认。

### 2. 读素材，学机制不搬台词

有素材时先读用户拥有使用权的原文，再读对应拆文报告；原文是语感、顺序和具体行为的依据，拆文报告只是索引。`拆文库/` 中的 ASR 原稿可用于研究：感官动作、数字推进、称谓变化、回旋镖台词和首尾物件，但不得复制原句、整段改名或把拆文报告的评价当事实。

需要现实细节时才搜索：职业流程、场地、价格、法规、设备等必须查证；纯粹为了凑「八路检索」或给笑点找网络段子，不得搜索。每个采用的事实记来源和用途；不把搜索数量写成质量分。

### 3. 写唯一剧本

默认 Markdown 方言：

```md
# EP001 集名

## EP001-SC001 内·合租屋·夜

动作、空间和可见状态变化。不要用「你感到很紧张」代替手抖、停顿、退后或做错动作。

甲：台词。
乙（压低声音）：台词。
[VO] 只有无法由画面/表演承载的信息才使用画外音。
[SFX] 声音事实只写对行动或信息有作用的声音。
```

- 场景标题必须能拍：内/外、地点、时间或天气；不需要镜号表。
- 每场至少有一个可表演动作；每句自写对白都必须在争取、试探、回避、施压、让步或重新定义关系。
- 每场都要改变信息、权力、关系、情绪、物理状态或风险中的至少一项；没有变化就删掉或合并。
- 核心阻力要有策略。对手不能只在主角说完后礼貌退场；主角也不能靠旁白宣布赢了。
- 开头第一拍给可见问题、异常动作或正在发生的冲突；不要先放账号问候、Skill 说明、抽象主题或审核结论。
- 结尾停在本集兑现/代价/新压力的有效位置；不强行追加 CTA、金句或「评论区报数」。若用户需要口播收尾，另交口播版本，不混入剧本。

### 4. 独立审读，再改稿

审读者先只读当前剧本和本集契约，不能以作者自评、旧报告或机器绿灯代替正文判断。报告要给具体场景和原句/行号：最早失去追看的位置、目标与阻力、行动结果、最弱对白、最像说明书的段落、结尾是否兑现，以及具体改法。

同一主会话可以按「主笔 → 审读 → 主笔」三个明确步骤执行，但不得把自己写的检查清单冒充独立多人会审。没有独立审读时，状态必须是 `PROVISIONAL`；不输出「好看」「通过」「必爆」等空结论。

### 5. 机械检查只检查机械事实

运行：

```bash
python3 skills/arena-screenplay/scripts/arena_screenplay_check.py 剧集/EP001/剧本.md --json
python3 skills/arena-screenplay/scripts/arena_screenplay_review.py 剧集/EP001/剧本.md --output 审核/EP001.md
```

检查器只验证文件是否存在、场景标题和对白格式、空场、明显审计元话语、哈希绑定等。它的结果使用 `mechanical_status` 与 `editorial_status` 两个字段，**机械 PASS 绝不等于剧本通过**。它不会判「剧情水不水」、不会数关键词冒充笑点、不会把检索路数/物证数当质量分。

## 质量闸门（人读）

按需读取：

- [剧本契约](references/剧本契约.md)：输入、目录、格式和状态命名；
- [抖音原生剧本](references/抖音原生剧本.md)：短视频观看节奏与口播/剧本分界；
- [拆文语料使用](references/拆文语料使用.md)：当前拆文库与最新错误稿的对照；
- [审读契约](references/审读契约.md)：独立审读、证据、哈希绑定和发布边界。

本 Skill 不规定固定字数、固定 5–8 场、每 15–25 秒翻面、三件物证、八个笑点或必须反杀。它们可以是某集的创作选择，不能被当作通过条件。

## 诚实边界

- 题面事实、用户持有素材和检索事实分开标记；事实不确定就写 `待核`，不让机器默默补齐。
- 研究样本可以说明「原稿怎样工作」，不能证明新稿会爆；任何平台数据都记录样本日期、来源和不确定性。
- 机械检查、主笔自检、独立审读、成片试听、平台发布数据是五件不同的事。缺哪件就明确缺哪件。
